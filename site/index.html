Regression testing for AI features

Your prompts change. Quality only moves one way.

Point it at your repo. It finds your prompts, writes the tests for you, and fails the build when quality slips. No eval suite to author, no harness to wire up.

$ npx prompt-ratchet scan

MIT licensed. Runs in your CI. Baselines live in your repo, not ours.

The problem

Your test suite is blind to the half of your product that matters

Someone edits a prompt, swaps a model, or reindexes your retrieval — and output quality quietly degrades. Traditional tests assert exact output, and model output is non-deterministic, so nothing catches it. You find out from a customer.

Eval platforms exist. Almost nobody keeps using them, for one reason: you have to write the test cases yourself. Writing evals is nobody's job and nobody's promotion, so the suite gets written once during a hackathon and then rots.

The idea it rests on

An LLM test does not pass or fail. It passes at a rate.

Run a case once and you have sampled a distribution exactly one time — you have learned almost nothing. So every case runs several times and Ratchet tracks the pass rate. A regression is a rate that dropped past a threshold. Anything smaller is sampling noise, and treating noise as failure is precisely how every flaky suite ends up disabled.

Baseline
100%

Three of three samples held. This is the bar.

Still fine
67%

One sample wobbled. Inside the threshold, so the build stays green — a binary test would have failed here and taught you to ignore it.

Regressed
33%

Two of three now fail. That is a real move, and the build stops.

How it works

Four commands, then it lives in CI

SCAN

Finds your prompts

Walks the repo for calls into a model SDK and extracts each prompt with its variables.

GENERATE

Writes the cases

Typical, edge, adversarial, injection, safety and format. Plain JSON you can edit.

RUN

Scores them

Each case several times, deterministic checks first, a judge only where meaning matters.

CHECK

Guards the branch

Diffs against your baseline, comments on the pull request, exits non-zero on a regression.

Endpoint mode

Test the feature, not just the prompt

A real feature is a prompt plus retrieval plus tool calls plus whatever you do to the output — and most production failures live in that "plus". Name a handler and Ratchet drives it instead, so what gets scored is what your users would have received. 

{
  "endpoints": {
    "support-triage": {
      "url":     "http://localhost:3000/api/support",
      "headers": { "authorization": "Bearer ${SUPPORT_TOKEN}" },
      "body":    { "question": "{{question}}" },
      "extract": "reply"
    }
  }
}

Your cases do not change

Only what answers them changes. Generate against the prompt, score against production.

Secrets stay in the environment

${ENV_VARS} resolve at call time, so no token ever lands in a config file you commit.

Being straight with you

What it does not do yet

  • Discovery needs the prompt visible in your source. Prompts assembled at runtime from a database will not be found — use endpoint mode and name the variables yourself.
  • Every case is one turn. Multi-turn conversations are not modelled.
  • Streaming endpoints need a complete body. Server-sent events are not parsed.
  • There is no hosted history. Baselines live in your repo as JSON. That is a feature at this size and a limitation later.
